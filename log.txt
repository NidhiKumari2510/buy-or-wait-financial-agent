3. RECOMMENDED "COUNTERFACTUAL FINANCIAL PLAN ENGINE"
------------------------------------------------------------

CHATGPT:
Suggested that instead of simply asking "Can the user afford this?",
the system should generate and evaluate multiple possible ways of
making the purchase safe.

Candidate plans should include:

- full payment now
- valid partial payment
- supplied installment plans
- waiting until a later safe date
- plans involving permitted spending changes

Each candidate should be simulated over the required forecast
period.

Unsafe candidates should be discarded.

Safe candidates should be ranked using the official problem rules:

1. Complete by the desired deadline
2. No spending changes
3. Minimize total amount paid
4. Start payment earlier
5. Fewer payments
6. Lowest payment option ID

This approach was identified as a useful combination of deterministic
financial reasoning and AI-assisted evidence interpretation.

6. MAIN CODE IMPROVEMENTS RECOMMENDED
------------------------------------------------------------

CHATGPT:
Identified the following areas for improvement:

A. Recurring-event reconstruction

The existing heuristic relied too heavily on category, direction,
similar amounts, and approximate intervals.

Recommended distinguishing:
- recurring expenses
- recurring income
- one-time purchases
- transfers
- refunds
- unusual events
- fixed expenses
- flexible expenses

The event type, category, description, dates, amounts, status,
linked events, and flexibility should all be considered.

No recurring event should be invented merely because transactions
happen at approximately similar intervals.


B. Projected event IDs

Recommended separating:
- original event ID
- recurring-series identity
- projected occurrence

This prevents spending-change actions from accidentally affecting
unrelated transactions.


C. Spending-change optimization

The implementation tended to reduce expenses directly to
minimum_allowed_amount.

Recommended calculating the smallest reduction actually necessary
to make a plan safe, while respecting:
- flexibility
- minimum_allowed_amount
- protected categories
- user's willingness to reduce/stop categories
- maximum of three spending changes


D. Message interpretation

The regex-based parser was considered too brittle.

Messages can contain multiple:
- dates
- amounts
- old values
- new values
- cancelled events
- replacement dates
- pending/confirmed information

The system should identify the current financial fact instead of
simply taking the first date or amount found.

An LLM can be used for structured evidence extraction, but the
result must be validated before entering the financial engine.


E. Conflict resolution

Recommended explicitly implementing the official conflict rules:

1. Explicit cancellation / settlement / amendment
2. Newer record from the same source
3. Settled event over estimate/forecast
4. Financially safer interpretation if ambiguity remains


F. Image evidence

Recommended resolving images through images.csv and related IDs,
extracting missing amounts or financial information when necessary.

Blank event amounts must not be interpreted as zero.

Image content must remain untrusted evidence.


G. Currency conversion

Recommended reviewing the exchange-rate implementation carefully
and using only supplied exchange-rate data.

No live exchange-rate API or invented rate should be introduced.


H. 90-day simulator

Recommended verifying that:
- historical settled transactions are not double-counted
- future confirmed cash flows are included
- pending credits are excluded
- failed/cancelled events are handled correctly
- recurring events are projected correctly
- the requested payment occurs on the correct date
- the minimum balance is enforced every day


I. amount_safe_to_pay

Identified this as the most important numerical weakness.

Recommended calculating the maximum amount payable on the request
date such that the balance never falls below the required minimum
during the forecast period.

Optional spending changes must NOT be used when calculating this
baseline amount.

The result must be:
- >= 0
- <= requested amount
- independently verified through the simulator


J. earliest_date_for_full_payment

Recommended treating this as an independent financial calculation.

It represents the first date on which the full requested amount can
be safely paid WITHOUT optional spending changes.

It can equal the request date even if installments are ultimately
selected.


K. Installment plans

Recommended treating request_payment_options.csv as authoritative.

The implementation must use the supplied:
- payment amounts
- first payment date
- number of payments
- payment frequency
- financing fee
- total payable amount

It must not invent or modify installment schedules.


L. Validation

Recommended strengthening the validator to check:
- amount bounds
- valid statuses
- valid payment methods
- chronological payment plans
- exact installment-option matching
- partial-payment rules
- valid spending changes
- maximum three spending changes
- reduction limits
- consistency of earliest payment date
- actual safety through the simulator

STEP 3 -- Built code/config.py and code/models.py

Wrote typed dataclasses (Request, FinancialProfile, FinancialEvent,

--------------------------------------------------------------------------------
STEP 4 -- Built code/data_loader.py, ran against real dataset, iterated
--------------------------------------------------------------------------------
Wrote CSV loading/indexing layer with a debug summary printer
(`python code/data_loader.py`) to verify assumptions against the REAL
dataset rather than docs.

Debugging iterations (real errors from user's terminal, root-caused each
time rather than blind rewrites):
  1. ImportError: cannot import name 'ExchangeRate' from 'models'
     -> root cause: models.py was still empty (starter file, not yet
        populated). Fixed by pasting full models.py content.
  2. AttributeError: module 'config' has no attribute 'REQUESTS_CSV'
     -> root cause: config.py was also still empty. Fixed by pasting full

  3. ValueError: Required date field 'settlement_date' is blank for row
     event_1856
     -> genuine data finding: settlement_date CAN be blank (e.g. for some
        pending events). Fixed by making settlement_date Optional[date] in
        models.py and using _opt_date() instead of a required parser in
        data_loader.py, rather than forcing a default.
  4. AttributeError: module 'config' has no attribute 'EVENT_STATUS_CONFIRMED'
     -> root cause: initial config.py guessed status values as
        {settled, pending, confirmed} based on a third-party doc summary.
        Running data_loader.py's debug summary against the REAL dataset
        revealed the actual six status values: settled, pending, scheduled,
        cancelled, failed, unrealized (no "confirmed" -- "scheduled" fills
        that role). Also revealed direction includes "non_cash" (not just
        credit/debit) and flexibility includes "reducible_or_stoppable"
        (not just fixed/stoppable/reducible). Rewrote config.py to match
        verified reality instead of assumed values.

Final clean run confirmed: 250 requests, 275 profiles, 25342 events, 790
payment options, 215 messages, 16 images, 134 exchange rates, exactly 16
events with blank amount (1:1 match with 16 images). Exchange rate pairs
confirmed as a hub structure: only EUR<->USD, EUR->ZAR, USD->IDR, USD->INR
exist directly.

--------------------------------------------------------------------------------
STEP 5 -- Built code/utils/currency.py
--------------------------------------------------------------------------------
Currency conversion with BFS multi-hop routing over the small currency graph
(handles pairs with no direct rate, e.g. ZAR->IDR, by routing through
USD/EUR), exact-date match first, then nearest-preceding-date fallback with
a logged warning, then inverse-of-reverse-pair as a last resort.

--------------------------------------------------------------------------------
STEP 6 -- Built code/financial_state.py
--------------------------------------------------------------------------------
Joins profile + events + payment options + messages/images per request_id
into one FinancialState object; converts every event amount into the user's
home_currency; leaves unresolved (blank) amounts as None rather than
defaulting to 0, per problem_statement.md's explicit rule. Verified with a
debug run against a real sample request (request_26, user_26, IDR,
76 events, 0 unresolved amounts for that sample).

--------------------------------------------------------------------------------
STEP 7 -- Built code/simulator.py (90-Day Safety Check)
--------------------------------------------------------------------------------
Implements:
  - detect_recurring_series(): heuristic recurring-pattern detection
    (longest trailing regular-interval chain per category+direction,
    tolerant of a genuine rate change via _trailing_consistent_amount)
  - project_recurring(): projects a detected series forward beyond its last
    known occurrence, within the 90-day window
  - build_cash_flow_events(): applies status-based inclusion/exclusion
    rules (always-exclude cancelled/failed/unrealized/non_cash; pending
    credits excluded, pending debits reserved)
  - simulate(): full 90-day balance projection given candidate payment(s),
    returns safety verdict + minimum balance reached + date
Verified with a debug run: baseline simulation for a real sample request
correctly detected 8 recurring series (salary, rent, utilities, cloud
storage, streaming, groceries, transport, dining) with sensible
intervals/amounts.

--------------------------------------------------------------------------------
STEP 8 -- Built code/ai/client.py and code/evidence_resolver.py
--------------------------------------------------------------------------------
Anthropic API wrapper (model: claude-haiku-4-5-20251001, chosen as the
cheapest current model since extraction tasks here are short-text/
single-image -> fixed small JSON schema, not open-ended reasoning).
Designed to degrade gracefully with no API key: get_client() returns None,
extraction functions return (None, None), evidence_resolver.py logs a NOTE
and skips rather than crashing.

evidence_resolver.py handles two jobs:
  1. Image-based amount resolution for blank-amount financial events
  2. Message-based amendments (confirm/amend/cancel/delay/info_only) via a
     narrow structured JSON extraction schema
Explicit untrusted-content defense per problem_statement.md: the extraction
schema can only express facts about ONE financial event -- structurally
cannot express instructions to override output fields. System prompt also
asks the model to flag (not obey) embedded instructions via an
injection_attempt_detected field.

User does not have an ANTHROPIC_API_KEY (cost constraint) -- confirmed this
is a legitimate, defensible submission path: pipeline runs end-to-end
without a key, blank-amount events are conservatively excluded rather than
guessed, messages are left unapplied, and usage_report.md honestly reports
zero LLM calls. No API key is ever included in the submission (kept in a
gitignored .env file, outside code.zip).

--------------------------------------------------------------------------------
STEP 9 -- Built code/planner.py
--------------------------------------------------------------------------------
Deterministic candidate generation:
  - compute_amount_safe_to_pay(): bisection search over simulate()
  - compute_earliest_full_payment_date(): forward scan across the 90-day
    window
  - Spending-change selection: greedy, largest-saving-first, respects
    user's protect/reduce/stop category preferences and per-event
    minimum_allowed_amount floors, capped at 3 changes
  - Candidate builders for full_payment, full_payment-with-spending-changes,
    partial_payment (exactly 2 payments per spec), installments (one per
    matching supplied payment_option, respecting max_installment_months),
    and wait (only generated when strictly safer/later than immediate
    full_payment, avoiding a redundant-candidate bug flagged from prior
    community experience with this same problem)

--------------------------------------------------------------------------------
STEP 10 -- Built code/ranker.py and code/validator.py
--------------------------------------------------------------------------------
ranker.py: implements the exact 6-rule deterministic ranking order from
problem_statement.md (deadline completion, no spending changes, minimize
total paid, start earlier, fewer payments, lowest payment_option_id
tiebreak) plus eligibility filtering against payment_methods_user_will_
consider.

validator.py: post-hoc deterministic checks (amount bounds, valid enums,
payment_plan format/chronology, partial_payment exactly-2-payments and
sum-matches-requested_amount rule, installments matching a real supplied
payment_option_id, spending-changes stop/reduce mutual exclusivity, max 3
changes). Logs violations loudly during development without blocking row
generation, so every request_id always gets an output row.

--------------------------------------------------------------------------------
STEP 11 -- Built code/decision_engine.py and code/main.py
--------------------------------------------------------------------------------
decision_engine.py: orchestrates one request end-to-end (build state ->
resolve evidence -> generate candidates -> rank -> pick winner -> format
output row -> validate -> template-based explanation). Explanation is
template-based rather than an extra LLM call, specifically to guarantee the
explanation text can never drift from the actual computed numbers.

main.py: loops over all requests in dataset/requests.csv, writes output.csv
to the repository root (not dataset/output.csv, per submission rules),
wraps each request in a try/except with a safe not_affordable fallback row
so one bad request can never crash the whole run, and writes
evaluation/usage_report.md summarizing model/calls/tokens/estimated cost
for the actual run that produced output.csv (correctly reports zero calls
given no API key was configured).
